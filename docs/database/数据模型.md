# 数据模型说明

> 本文件由 `tools/gen_data_model.py` 从 `sql/01_schema.sql` 生成：**生成区不要手改**，改表之后跑一次 `python tools/gen_data_model.py` 重生成。文末「手写说明」标记之间的**手写区可以编辑，重生成时整段保留**。

库名 `pet_clinic`，MySQL 8，字符集 `utf8mb4`，共 12 张表、210 个字段。

## 一个前提：没有物理外键

`sql/01_schema.sql` 里 `FOREIGN KEY` 约束数量为 0，表间关系全部是**逻辑外键**（`xxx_id` 列加普通索引），完整性由服务层保证。这样做的取舍：

- 两个脚本可以反复整库导入，不会被建表顺序卡住；
- 字段改名或换库不需要先 ALTER 约束；
- 代价是数据库不替你兜底，跨表写入必须留在同一个 `@Transactional` 服务方法里。

另有 9 张表带 `deleted` 走逻辑删除（MyBatis-Plus 全局配置），其余 3 张刻意不带：`doctor_schedule`、`consult_session`、`consult_message`。

下面这段是手写的逐表业务说明，重新生成本文件时会被原样保留。

## 逐表说明

### `sys_user` — 宠物主人

注册与登录主体。`username` 唯一索引，`phone` 普通索引（后台按手机号找人）。`status=0` 为禁用，禁用后 REST 与 WebSocket 都会拒绝。`deleted` 逻辑删除。

### `pet` — 宠物档案

`user_id` 指向主人，一只宠物可有多次就诊记录，故为 1:N。`age_month` 是冗余的月龄，为避免列表页每次算日期差；`vaccine_status`、`deworm_flag`、`allergy`、`medical_history` 是医生接诊时要看的临床字段。

### `department` — 科室

`code` 唯一（如 `NK` 内科）。`icon` 直接存 emoji，省掉一套图标资源。停用科室不影响历史单据，因为预约单上冗余了 `department_id` 且在下单时已快照。

### `doctor` — 医生

`department_id` 所属科室；`title` 职称；`specialty` 逗号分隔的擅长领域；`consultation_fee` 问诊费，下单时快照到 `appointment.amount`。

三个字段是**聚合回填**而非实时计算：`rating`（综合评分）、`review_count`（评价数）、`appointment_count`（累计完成接诊数）。写入时机是新增评价、评价显隐变更，以及后台「刷统计」手工触发。医生编辑请求使用 `DoctorForm`，不包含这些字段；请求体即使伪造也会被忽略。

`online_status` 由 WebSocket 的连接建立 / 断开维护，不是心跳字段——进程重启会残留在线脏值，属可接受的展示误差。

### `admin_user` — 后台账号

管理员与医生共用这张表，靠 `role`（`ADMIN` / `DOCTOR`）区分；`role=DOCTOR` 时 `doctor_id` 绑定到 `doctor.id`，且该唯一关系上建了索引。也就是说**医生的业务身份在 `doctor` 表，登录身份在 `admin_user` 表**，接口层通过 `LoginUser.doctorId` 把两者接起来，从而保证医生只能看到分给自己的工单与会话。

### `doctor_schedule` — 排班与号源

一个医生、一天、一个时段一行。`(doctor_id, work_date, period)` 上的**唯一索引**是批量排班能重复执行的前提：按周模板批量生成时，已存在的时段直接跳过，不会覆盖已经放出去的号。

`total_num` 是号源总数，`remain_num` 是剩余号源，`last_queue_no` 是该排班的发号计数器。创建预约时先锁读排班，再通过带 `status=1 AND remain_num>0` 条件的 UPDATE 同时扣减余量、递增计数器。`status=0` 表示停诊，语义是「关号但保留已成交预约」。

此表没有 `deleted` 列：停诊与删除是两个不同动作，删除走物理删除且要求该时段无预约。

### `appointment` — 预约单（核心）

`order_no` 唯一，形如 `PC20260913025148316`。

两组状态分开建模，这是本表最重要的设计：

- `status`：就诊流转 — 0 待接诊 / 1 已接诊 / 2 已完成 / 3 已取消 / 4 未到诊
- `pay_status`：资金流转 — 0 未支付 / 1 已支付 / 2 已退款

两组状态分别描述就诊和支付，例如「已支付、待接诊」与「已退款、已取消」。模拟支付成功时 `pay_type` 记为 `MOCK`。

`queue_no` 来自占号后读取的 `doctor_schedule.last_queue_no`，不再由 `total_num - remain_num` 推算。`AppointmentService.create` 在同一事务内调用 `tryOccupy`、`selectLastQueueNoForUpdate` 并保存预约。创建成功后再取消，只恢复余量，不回退发号计数器，也不回收原预约的号码，因此允许跳号，号码也可能超过号源总数。若创建事务本身回滚，本次扣减与计数递增一起撤销。

`appointment_date`、`period`、`start_time`、`end_time`、`department_id` 都是从排班与医生快照过来的，好处是医生事后改排班不会扭曲历史单据。

`is_reviewed` 与 `doctor_review.appointment_id` 唯一索引配合，构成「一单一评」的双重保险。

索引组合按查询场景来：`user_id`（我的预约）、`doctor_id + appointment_date`（医生某天的接诊列表 / 看板）、`schedule_id`（号源回查与回滚）、`status`（定时任务扫超时未支付）。

### `consult_session` — 图文会话

图文问诊免费、不限量、不建订单：患者在医生主页选宠物、填症状即落一条会话（0 待接诊），医生在会话列表或聊天室里点「接诊」后开始沟通（`start_time`），医生结束问诊时置 2（`end_time`）并拒绝后续消息；医生一直不接诊时，患者可以自己关掉待接诊的会话。

`symptom` / `images` 是发起时填的病情描述与患部照片；`summary` 是医生结束时写的问诊小结（线上只建议、确诊要面诊），展示在患者会话页顶部。

`appointment_id` 是历史遗留列：早期版本图文问诊挂在预约单下、支付时开会话，现在这一列对新数据恒为 NULL，只保留旧数据的联系。`uk_appointment_id` 唯一约束也随之保留。

`user_unread` / `doctor_unread` 两个方向的未读计数分别维护，配合 `last_message`、`last_message_time` 让会话列表一次查询就能渲染，不需要对消息表做聚合。

`moderate_status` / `moderate_reason` / `moderate_by` / `moderate_time` 是**管理员处置轴**，与 `status` 的诊疗生命周期正交（同 `appointment` 把就诊与资金两个状态拆开的思路）：1 无效关闭 / 2 违规屏蔽；非 0 时参与方视同会话不存在（列表与未读过滤、各入口 404），管理员审计视图仍可见。非 0 且会话未结束时会连带关闭并留一条系统消息。

无 `deleted` 列，会话是诊疗过程的法定记录，不做删除；处置同样只改标志位。

### `consult_message` — 会话消息

`sender_role`（`USER` / `DOCTOR` / `SYSTEM`）与 `msg_type`（`TEXT` / `IMAGE` / `SYSTEM` / `SUGGEST`）分开：文字与图片是内容维度，系统消息是角色维度。`SUGGEST` 是医生的「建议到院」卡片，只有医生能发，患者侧渲染成带「去预约挂号」按钮的消息（`content` 存医生选填的附言）。图片消息的 `content` 存的是上传接口返回的 URL，聊天帧里也只传 URL，因此 WebSocket 单条消息上限 16KB 足够。

`sender_id` 在系统消息时为 0。冗余 `sender_name`、`sender_avatar`，避免历史消息渲染时回表查用户。

两个索引对应两条真实查询：`(session_id, create_time)` 翻页取历史，`(session_id, is_read)` 标记已读与统计未读。

`hidden` / `hidden_reason` / `hidden_by` / `hidden_time` 是管理员对单条消息的屏蔽标记（显式业务列）：参与方的历史/最近消息与已读回执都过滤 `hidden=1`，管理员审计视图不过滤、原样带 `hidden=1` 返回。

无 `deleted` 列，理由同会话；屏蔽也不走 `deleted`（见"通用列约定"）。

### `medical_record` — 电子病历

`record_no` 唯一。一张预约单一份病历（服务层按 `appointment_id` 查改，重复提交即为修订）。五个 `xxx_id` 冗余快照，使病历能脱离预约单独立按用户、宠物、医生、科室检索。

`next_visit_date` 支撑病历详情页的「建议 X 日回院复查 + 去预约」入口。`images` 存检查影像 URL 列表。

### `doctor_review` — 就诊评价

`appointment_id` **唯一**，一单一评在库层面兜死。三维评分：`rating` 综合、`attitude_score` 服务态度、`effect_score` 诊疗效果。`is_anonymous=1` 时用户端只展示「匿名用户」。

`reply` + `reply_time` 是医生回复，公开展示在医生主页。`status`（0 隐藏 / 1 显示）由管理员治理，切换时会触发医生评分重算——隐藏一条差评确实应该改变公开评分。

### `notice` — 公告与养宠科普

`type`：1 公告 / 2 活动 / 3 养宠科普。`status`：0 草稿 / 1 已发布 / 2 下架，用户端只查已发布。`top_flag` 置顶，`view_count` 在详情接口里累加。
`publish_time` 与 `publish_by` 只在**首次**转入已发布时写下，下架后重新发布不刷新，所以两个值记的是「这条内容最早由谁在何时放出去」；草稿两者都为 NULL。编辑公告时表单会整份回传，这两列由服务端强制忽略，只能由发布动作产生。

## 通用列约定

- 主键 `id BIGINT AUTO_INCREMENT`，MyBatis-Plus `id-type: auto`。
- `create_time` / `update_time` 全部 `DATETIME DEFAULT CURRENT_TIMESTAMP`，后者带 `ON UPDATE`，不在代码里手工赋值。
- 有业务存续意义的表带 `deleted TINYINT`，由 MyBatis-Plus 全局逻辑删除接管（配置 `logic-delete-field: deleted`），因此所有查询自动追加 `deleted = 0`。`doctor_schedule`、`consult_session`、`consult_message` 例外，没有该列。
- 管理端的「屏蔽」刻意**不复用 `deleted`**：全局逻辑删除会让管理员审计视图也被注入 `deleted=0`，把被屏蔽行一起藏掉，破坏"完整可追溯"；且 `consult_session` / `consult_message` 还有手写 SQL 不吃注入，两套口径必然打架。所以 `consult_message.hidden` / `consult_session.moderate_status` 是**显式业务列**，由各查询点自行决定过不过滤。
- 枚举值一律用 `TINYINT` + `COMMENT` 说明；中文文案的单一事实源是前端 `utils/dict.js` 里的枚举表，页面一律通过 `text()` / `options()` / `tagType()` 取词，不允许在页面里另抄一份字面量。
- 金额 `DECIMAL(10,2)`，不用浮点。
- 多图与多值字段（`specialty`、`images`）用逗号分隔的 `VARCHAR`，项目规模下不值得引入关联表，代价是无法按单张图检索。
