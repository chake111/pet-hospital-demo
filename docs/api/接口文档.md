# 接口文档

后端所有 REST 接口由 Spring Boot 提供，统一挂在 `server.servlet.context-path = /api` 之下。

- 开发环境：Vite 在 `http://127.0.0.1:5173`，把 `/api` 代理到 `http://127.0.0.1:8081`，不重写路径，所以浏览器 Network、curl、Swagger UI 看到的路径完全一致。
- 在线文档（Swagger UI）：`http://127.0.0.1:8081/api/swagger-ui/index.html`；OpenAPI 原始描述：`/api/v3/api-docs`。
- 本文按端分组列出全部接口的用途与权限，参数细节以在线文档为准。

## 统一响应结构

**应用业务响应的 HTTP 状态码恒为 200，业务结果看响应体里的 `code`。** 前端 axios 拦截器只判断 `body.code`，不判断 `res.status`。**HTTP、代理与网络层错误不走这套约定**：后端没起、代理 502、超时这类错误根本到不了应用层，响应里没有 `body.code`，前端由 axios 错误分支统一提示"连接失败 / 请求超时"，不与业务码混判。

```json
{ "code": 200, "msg": "ok", "data": { } }
```

| code | 含义 | 前端行为 |
| --- | --- | --- |
| 200 | 成功 | 取 `data` |
| 400 | 参数校验失败 / 业务规则不满足（含上传文件过大） | 弹出 `msg` |
| 401 | 未登录、token 失效、账号被禁用 | 清除对应侧 token，整页跳转登录页 |
| 403 | 已登录但无权（角色不符、访问他人数据、管理员执行医生操作） | 弹出 `msg` |
| 404 | 路径未匹配到任何接口 | 弹出 `msg` |
| 405 | 请求方法不被支持 | 弹出 `msg` |
| 500 | 未捕获异常兜底 | 弹出 `msg` |

配置了 `default-property-inclusion: non_null`，`data` 为空时整个字段不出现，前端不要假设它一定存在。时间统一 `yyyy-MM-dd HH:mm:ss`（日期 `yyyy-MM-dd`，时间 `HH:mm:ss`），时区 `Asia/Shanghai`，都在 `JacksonConfig` 里全局设定。

分页响应统一为：

```json
{ "records": [], "total": 0, "current": 1, "size": 10, "pages": 0 }
```

分页请求参数统一为 `pageNum`（默认 1）、`pageSize`（默认 10）。

## 认证与权限

**登录态**：JWT（HMAC-SHA；算法由 jjwt 按密钥长度自动选择——≥32 字节→HS256、≥48→HS384、≥64→HS512），有效期 7 天，密钥与请求头名在 `application.yml` 的 `petclinic.jwt` 下。凭据放在 `Authorization: Bearer <token>`。

**密钥没有默认值**：`JWT_SECRET` 未设置、短于 32 字节或仍是历史示例值，启动自检直接失败；本地开发同样要先 `export JWT_SECRET`。

**令牌内容**：账号 id、类型（`typ`）、角色、展示名与头像、医生账号的 `doctorId`，以及版本号 `ver`（取自账号表 `token_version`）。`AccountGuard` 每次校验都比对库中当前版本：**账号本人改密会在同一条 UPDATE 里把 `token_version + 1`，此前签发的令牌立即失效**；管理员停用账号在下一个请求被拒；轮换 `jwt.secret` 则所有令牌一并失效。

**鉴权规则**由 `AuthInterceptor` 按路径前缀判定，不认第二份 token：

| 前缀 | 要求的账号来源 |
| --- | --- |
| `/admin/**` | `admin_user`（管理员或医生） |
| `/client/**` | `sys_user`（宠物主人） |
| `/common/**` | 任一已登录身份 |

免登录白名单只有 4 条：`/client/catalog/**`（所有只读展示类接口收在这里）、`/client/auth/login`、`/client/auth/register`、`/admin/auth/login`。

前缀判定解决「你是哪一侧的人」，`@RequireRole` 解决「你能不能干这件事」。需要留意的一个约定：**管理员不参与问诊对话**——发言、已读、未读、接诊/结束这些医生动作仍锁 `DOCTOR`（管理员账号体系里没有 `doctorId`，调用一律 403）；管理员在后台「问诊记录」页有**只读**入口（`/admin/consult/page` 与 `/{id}/messages`），用于合规追溯，不清未读、不能发言。

**数据隔离**不靠接口逐个判断，而是在服务层按身份收敛：医生账号访问工单、病历、评价、会话时自动追加 `doctor_id = 自己的 doctorId`；患者访问时自动追加 `user_id = 自己`。所以不存在「传个别人的 id 就能看到别人数据」的口子。

## 写接口请求体

科室、医生、公告、宠物、病历的写接口使用各自的 Form DTO：`DepartmentForm`、`DoctorForm`、`NoticeForm`、`PetForm`、`MedicalRecordForm`。表单只接收可编辑字段；`id`、`deleted`、`createTime`/`updateTime` 以及各聚合字段（医生评分/评价数/接诊量/在线状态、公告阅读量/发布人/发布时间、宠物归属、病历编号/归属/就诊日期）不在表单里，请求体即使带了也会被忽略，统一由服务端或 MyBatis-Plus 填充策略维护。读接口仍返回原实体/VO，响应结构不变。

两个可空字段使用「省略 = 保持原值，显式 `null` = 清空」的约定：宠物 `birthday`/`weight`、病历 `nextVisitDate`。

### 科室 `DepartmentController` / 医生 `DoctorController` / 排班 `ScheduleController` / 公告 `NoticeController`

四组都是标准 CRUD 加一个状态开关，权限粒度如下（这是后台权限设计的主要落点）：

- 写操作（新增、修改、删除、启停、批量排班）与 `/admin/doctor/{id}` 编辑表单详情（含手机号原值）要求 `ADMIN`；医生端的展示与下拉走免登录的 `/client/catalog` 目录接口，不经过 `/admin/doctor/{id}`；
- 放宽到 `ADMIN + DOCTOR` 的读接口：`/admin/department/list`、`/admin/department/page`、`/admin/doctor/page`（供医生在接诊/写病历时选科室与同僚）；`/admin/schedule/page` 医生也可用，但服务端只返回本人排班（「我的排班」页）；
- 额外两个动作：`PUT /admin/doctor/{id}/refresh-stats` 重算评分与接诊量，`PUT /admin/schedule/{id}/stop` 与 `/resume` 分别是「关号保留已成交预约」和「恢复可预约状态，保留当前号源余量」（停诊只翻状态位、不清零，恢复时也不按订单回算——停诊期间的取消照常走 release 退回余量）。

科室编码 `code` 必填且非空；科室与医生状态只接受 `0/1`；公告 `type` 只接受 `1–3`、`topFlag` 只接受 `0/1`。医生新增不传状态按 `1`，编辑不传保持原值；公告新增不传状态按草稿，编辑不传保持原值。医生编辑与停诊/恢复共用同一状态写入路径，`onlineStatus` 由该路径维护。

排班修改有一条硬约束：**总量不能改到已放号数以下**，否则返回 400。

公告的发布留痕只记首次：`status` 变为已发布且 `publish_time` 为空时写入 `publish_time` 与 `publish_by`（当前登录账号），下架后重新发布不刷新，草稿两列恒为 NULL。用户端详情会抹掉 `publish_by`，不对外暴露后台账号 id。

### 统计 `StatsController`

`GET /admin/stats/dashboard` — 看板汇总，前端提供 7/14/30 天选项。返回数字卡片（今日预约与分流、今日营收、在线医生、用户与宠物数、待回复评价、超时未支付）及四组图表数据：`trend`（趋势）、`statusDist`（状态分布）、`deptDist`（科室预约量）、`topDoctors`（医生接诊量排行）。不再返回 `consultTypeDist`（问诊方式分布）。医生账号的预约、营收、待回复评价、未支付预约及前三组图表按本人医生身份统计，用户与宠物数按本人服务对象统计；医生数量、在线医生数量及接诊排行仍为全院口径。

## 公共接口 `/common`

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/common/upload` | 上传单张图片，返回可访问 URL，表单字段名 `file`。多张由前端逐张调用（症状图最多 6 张） |

需要任一已登录身份（患者或后台均可，前端由 axios 实例按 `config.kind` 决定带哪侧 token）。限制：类型与单文件 5MB（`petclinic.upload.max-size-bytes`），multipart 层再放宽到单文件 10MB / 单次请求 30MB。

返回的 URL 形如 `/api/uploads/2026/09/13/xxx.png`（按天分目录），**是完整可访问路径**，前端 `<img :src="url">` 直接用，不再拼 baseURL。图片以静态资源方式暴露、不经 Controller 读流；这里有个容易踩的坑：Spring 的资源映射模式在 `context-path` **之内**匹配，所以注册时必须把 `/api/uploads` 里的 `/api` 剥掉（见 `WebMvcConfig#resourcePattern`），否则真实地址会变成 `/api/api/uploads/**`，库里存的路径全部打不开。

## WebSocket 协议

地址：`ws://<host>/api/ws/consult?token=<JWT>`，可选再带 `&sessionId=<id>` 表示连上即进房。

浏览器建立 WebSocket 时不能自定义请求头，所以握手只能把 token 放在查询串里——**这是全项目唯一允许 `?token=` 的地方**，REST 接口明确拒绝从查询串取 token（`AuthInterceptor`），避免多一条鉴权旁路。握手阶段除了校验令牌，还会回查账号当前状态，因此禁用账号无法新建连接；但**已经建立的连接不会因此断开**（`AccountGuard` 在握手与每次 REST 请求时执行，不逐帧执行），要等到对方重连才生效。

前端发出的帧：

| type | 载荷 | 作用 |
| --- | --- | --- |
| `SUBSCRIBE` | `sessionId` | 进房，服务端回 `HISTORY` |
| `CHAT` | `sessionId`、`msgType`、`content` | 发消息；`msgType` 取 `TEXT` / `IMAGE` / `SUGGEST`——`SUGGEST` 是医生的「建议到院」，只有医生能发、附言选填，患者侧渲染成带「去预约挂号」按钮的卡片；图片消息 `content` 为 URL |
| `READ` | `sessionId` | 我已读，清零我的未读并通知对侧 |
| `PING` | — | 心跳 |

服务端下发的帧：

| type | 载荷 | 含义 |
| --- | --- | --- |
| `READY` | `name` | 连接就绪 |
| `HISTORY` | `messages`、`sessionId` | 进房时的最近消息，**已按时间正序** |
| `MSG` | `message` | 新消息，广播给房间内双方 |
| `READ` | `sessionId`、`role`、`readMessageIds` | 对侧已读；`readMessageIds` 是**本次事务实际由未读改为已读的消息 ID 增量集合**（不是全部历史，被屏蔽消息不在内）。单帧最多 200 个 ID，超过分多帧下发；没有新标记时仍发一帧空数组回执。subscribe（含握手自动订阅）与显式 `READ` 都走这条广播，增量被订阅消费后同样通知对侧 |
| `PRESENCE` | `doctorOnline` | 医生上下线 |
| `PONG` | — | 心跳响应 |
| `ERROR` | `msg` | 发送失败等原因；若在 `HISTORY` 到达前收到（会话同步失败），前端停止重连并进入终止态，提示刷新页面 |

几条实现约定，前后端都要守：

- REST 的历史分页是**倒序**（最新在前，便于翻页），而 `HISTORY` 帧是**正序**，两者排序方向不同是有意的。

聊天面板首次进入和断线重连均以 WebSocket HISTORY 恢复最近 20 条消息，不再另发 REST 首屏查询。重连会重置已加载窗口，更早消息可重新加载。两个会话历史 REST 接口支持可选正整数 `beforeId`，仅返回 id 小于该值的消息，按 id 倒序；total 为该过滤条件下的数量。聊天面板使用 pageNum=1、pageSize=20 和当前最小消息 ID 翻页。不传 beforeId 时保留原有页码分页，管理员审计权限及屏蔽可见性不变。被其他页面顶号（关闭原因 replaced）后停止自动重连，需要用户刷新重新进入。
- `READ` 只广播给对侧，发送方拿不到回执，因此「我的未读角标」不能靠 WS 帧即时收敛——界面在路由切换时重新拉一次 `/unread`，另有 30 秒兜底轮询。
- `READ.readMessageIds` 是增量精确 ID 集合：每个 ID 必须是正安全整数；新前端对缺少数组、含非法 ID 或单帧超过 200 个的整帧忽略，不凭较小 ID 推断已读（被屏蔽后恢复的消息在收到针对它的回执前仍显示未读）。**新旧协议不构成兼容完整验收**：部署必须后端先、前端随即更新，旧页面需刷新；短暂混用期间已读提示可能延迟，不得保留有缺陷的边界推断作兼容回退。
- 单条文本消息上限 16KB；图片先走 `/common/upload` 再在聊天里传 URL。
- 会话结束后服务端拒绝 `CHAT`，前端同时隐藏输入框做双保险。
